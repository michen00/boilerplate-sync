# Automated releases with release-please

Status: approved, not yet implemented
Date: 2026-08-04

## Problem

Releasing `michen00/boilerplate-sync` is five manual steps with no automation:

1. A hand-written `chore: bump version to X` PR touching `package.json`
2. Manual tag creation
3. `make release VERSION=vX.Y.Z` → `gh release create --generate-notes`
4. Manual `v1` alias move
5. Nothing updates `CHANGELOG.md`

Step 5 is a live bug. `CHANGELOG.md` contains `Unreleased`, `1.0.1`, `1.0.0`, but a
full `git cliff` run emits `Unreleased`, **`1.0.4`**, `1.0.1`, `1.0.0`. The `1.0.4`
section — which documents `fix(sync): reject globs in file_pairs sources` (#120) — is
missing from the file. Cause: `changelog-autoupdate.yml` only rewrites the
`Unreleased` section; nothing promotes it to a version heading at tag time, so every
release silently drops its own changelog entry. (`1.0.2` and `1.0.3` are legitimately
absent — those ranges held only `chore`/`ci`/`docs` commits, which `cliff.toml` skips.)

Two further symptoms of the manual process:

- **Release notes and the changelog have diverged.** `--generate-notes` publishes
  GitHub's autogenerated list, so `cliff.toml`'s curated grouping never reaches
  the people reading releases.
- **Tag signing lapsed.** `v1.0.0`–`v1.0.3` are annotated and carry valid
  signatures; `v1.0.4` and `v1` are annotated but unsigned. A step that depends on
  remembering eventually gets forgotten.

## Goals

- One human touchpoint per release: approve and merge a release PR.
- Tooling decides _when_ a release is warranted; the human decides _whether_ to ship.
- `CHANGELOG.md`, `package.json`, `package-lock.json`, the tag, the `v1` alias, and
  the GitHub Release all stay consistent without manual steps.
- No loss of security or integrity relative to today.

## Non-goals

- Publishing to npm. `package.json` version is repo metadata only.
- Preserving GPG-signed tags (see "Integrity analysis").
- Altering existing tags or GitHub Releases. Only `CHANGELOG.md` is rewritten; the
  published releases for `1.0.0`–`1.0.4` stay exactly as they are.

## Chosen approach

release-please in **PR-only mode**, with tag and release creation handled by our own
job.

```text
feat/fix merges to main
        ↓
release.yml  (on: push[main] + workflow_dispatch)
  job gated on github.ref == refs/heads/main
        ↓
  googleapis/release-please-action@v4  (App token)
    createPullRequests() maintains ONE open PR:
      chore(main): release 1.0.5
        package.json               1.0.4 → 1.0.5
        package-lock.json          1.0.4 → 1.0.5
        CHANGELOG.md               + ## [1.0.5] section
        .release-please-manifest.json
        ↓
   ← HUMAN APPROVES + MERGES        (the only touchpoint)
        ↓
same workflow, on the merge push:
  VERSION=$(jq -r '.["."]' .release-please-manifest.json)
  has v$VERSION a published release?  → yes: exit, nothing to do
                                      → API error: fail loudly
        ↓ no
  create ANNOTATED tag v1.0.5, push
  force-move ANNOTATED alias v1 → v1.0.5's commit
        ↓
  release-please-action@v4 again, same run:
    createReleases()      publishes the Release, attaching to the
                          annotated tag; clears autorelease: pending
    createPullRequests()  opens the next release PR
        ↓
release-provenance.yml fires on release:published — unchanged
marketplace-smoke.yml   fires on release:published — sees v1 already moved
```

### Why we pre-create the tag, and why release-please still publishes

`release-please-action` publishes via `POST /releases`, which mints a **lightweight** tag
when none exists — no tag object at all. Verified empirically across
`googleapis/release-please`, `googleapis/release-please-action` and
`googleapis/nodejs-storage`: every release tag in those repos is lightweight. Creating an
annotated tag ourselves _before_ that step means the Release attaches to a real tag object
with a message and tagger, and lets the `v1` alias move in the same pass.

**But release-please must still create the Release itself.** An earlier revision of this
design used `skip-github-release: true` and published the Release by hand. That is a trap:
release-please labels every release PR `autorelease: pending`, and the **only** code path
that clears it is `createReleasesForPullRequest` — which `skip-github-release` skips
entirely. `createPullRequests()` aborts outright while any merged release PR still carries
the label. The repo would therefore have opened exactly one more release PR in its
lifetime and then gone silent: every later push aborts, returns nothing, and exits 0.
Green forever, releases simply stop — the same "a step that depends on remembering gets
forgotten" failure the manual process had, only invisible.

Ordering makes this work in a single run: `main()` calls `createReleases()` **before**
`createPullRequests()`, so the label is cleared before it is read. The alias also moves
before this step, so `marketplace-smoke.yml` — which fires on `release: published` and
consumes `@v1` — sees the alias already correct.

### Manifest mode: omit `release-type`

`release-type` and `config-file` are **mutually exclusive modes** in
`release-please-action@v4`. `parseInputs` → `loadOrBuildManifest` branches on
`inputs.releaseType`: if it is set, the action calls `Manifest.fromConfig` with five
inline fields and **never reads `release-please-config.json`**. Manifest mode requires
_omitting_ the `release-type` input so it falls through to `Manifest.fromManifest`.

So `"release-type": "node"` goes in `release-please-config.json`, not in the workflow.
The same applies to `changelog-sections` and `include-commit-authors` — neither is
exposed as an action input.

### Idempotency

The release job keys off **the manifest version versus tag existence**, not the release
PR's title or commit message. `jq -r '.["."]' .release-please-manifest.json` gives the
version just merged; if `refs/tags/v$VERSION` already exists the job exits 0. This makes
re-runs and `workflow_dispatch` safe and does not depend on release-please's
`chore(main): release X` title convention holding across versions.

### Verified behaviour against real history

`npx release-please release-pr --dry-run --repo-url=michen00/boilerplate-sync
--release-type=node` was run against `main` at `08a9180`. It reported:

- `Would open 1 pull requests` — `chore(main): release 1.0.5`
- Changelog body containing exactly one entry: the undici fix (#168)
- Updates to `package.json`, `package-lock.json`, `CHANGELOG.md`,
  `.release-please-manifest.json`

All 27 other commits since `v1.0.4` — `chore`, `ci`, `build(deps)`, `docs`, `test` —
were correctly treated as non-releasable. This resolves the ambiguity between
release-please's `determineReleaseType` (which falls through to a patch bump for
unrecognized types) and its README (which gates PR creation on "releasable units"):
the README behaviour wins, and hidden types do not trigger releases. Dependabot
dependency bumps will therefore **not** prompt a release, matching the current
`cliff.toml` policy.

## Authorization and ruleset changes

`release-tags-protect` currently applies to `refs/tags/v*` and blocks `creation`,
`update`, and `deletion` while requiring signatures, with `RepositoryRole 5` (admin) as
the sole bypass actor. That conflates two kinds of tag with opposite requirements:
immutable `vX.Y.Z` releases and the deliberately movable `vX` alias.

Rescope it rather than granting a bypass actor:

```text
release-tags-protect
  include: refs/tags/v*.*.*     ← two literal dots: matches v1.0.4, v1.10.2;
                                  never matches v1, v2 … v100 (no dots)
  rules:   update    (block)
           deletion  (block)
  removed: creation             — only ever blocked automation
           required_signatures  — enforces nothing today (v1.0.4 and v1 are
                                  unsigned, created under admin bypass) and
                                  would block API tag creation outright
  bypass:  keep RepositoryRole 5 as a human escape hatch
```

The two literal dots do the separating, so no bracket expressions are needed and no
pattern maintenance is required when a `v100` major eventually ships. If a future scheme
introduces four-component tags, revisit — `v*.*.*` would match those too.

Consequences:

- Automation needs **no bypass actor, no PAT, and no new secrets**.
- Release tags become _more_ immutable than today: the App never gains authority to
  rewrite `v1.0.0`, and the `update`/`deletion` block stays in force.
- `main-protect` is untouched. release-please only opens PRs; nothing pushes to `main`.

### Token requirements

Both are load-bearing and non-obvious:

- **The release PR must be opened with the App token** (`vars.APP_ID` = 3959221,
  `secrets.APP_PRIVATE_KEY`), not `GITHUB_TOKEN`. PRs opened by `GITHUB_TOKEN` do not
  trigger workflows, and `main-protect` requires `Pre-commit hooks`, `build`, and
  `test-action` as status checks — the release PR would sit forever with no checks and
  be unmergeable. This matches how `readme-action-versions.yml` already mints a token.
- **The GitHub Release must be created with the App token.** Releases created by
  `GITHUB_TOKEN` do not emit `release: published`, so `release-provenance.yml` would
  silently stop attesting `dist/index.js` — losing the strongest integrity property in
  the repo, with no error surfaced anywhere.

## Integrity analysis

New tags will be annotated but **unsigned**. That is an accepted, bounded loss:

- **What signing bought here is small.** `release-provenance.yml` already generates
  SLSA build provenance for `dist/index.js` — keyless sigstore via OIDC, verifiable
  with `gh attestation verify dist/index.js --repo michen00/boilerplate-sync`. That
  binds the artifact consumers actually execute to the workflow and source commit that
  built it. A tag signature only asserts who created a ref. Provenance is the stronger
  and more relevant property for a published Action, and it is unaffected.
- **GitHub cannot sign tags on our behalf.** Web-flow signing covers commits only —
  every recent commit on `main` is `verified: true, valid`, including dependabot's and
  the App's. An annotated tag object created through `POST /git/tags` was probed
  directly and came back `verified: false, reason: "unsigned"`. GPG-in-CI is the only
  route to verified tags, and it requires both a signing key in CI and a bypass actor.
- **The practice had already lapsed** at `v1.0.4`, so this formalizes the status quo
  rather than regressing from a maintained invariant.

Net: lose signatures on new tags; keep SLSA provenance on the real artifact; gain
genuinely immutable release tags, no signing step to forget, and a `package-lock.json`
version that stops drifting.

## Blocker: two formatting hooks reject release-please output

release-please emits `*` bullets and **two** blank lines after each heading. Two
pre-commit hooks object, and `Pre-commit hooks` is a **required status check** on `main`,
so an unfixed release PR fails CI and can never be merged. A hook that _modifies_ a file
fails, so autofixing hooks are as blocking as reporting ones.

1. **markdownlint** — `.markdownlint.yml` sets `default: true`, so `MD004`
   (`ul-style: dash`) and `MD012` (`no-multiple-blanks`) are both active, and the hook
   runs with `--fix`. Line 1 of `CHANGELOG.md` already suppresses one rule; extend it:

   ```markdown
   <!-- markdownlint-configure-file { "no-duplicate-heading": false, "ul-style": false, "no-multiple-blanks": false } -->
   ```

2. **prettier** — runs on all markdown (`types_or` includes `markdown`) and
   `.prettierignore` contains only `dist`. It collapses consecutive blank lines and
   **does not read markdownlint directives**, so the fix above does nothing for it. Add
   `CHANGELOG.md` to `.prettierignore`.

Both are required. Fixing only markdownlint leaves prettier rewriting the file on every
release PR. release-please exposes no setting for bullet character or blank-line count,
so exempting the file is the only route.

## One-time migration

`CHANGELOG.md` is **fully regenerated** in release-please's format rather than left with
a format seam. Because the regeneration derives from `git log` and not from cliff output,
no step depends on `cliff.toml` still existing, so the order is unconstrained.

1. **Regenerate `CHANGELOG.md`** from scratch (see below).
2. **Extend the markdownlint directive** (above).
3. **Seed `.release-please-manifest.json`** with `{".": "1.0.4"}`.
4. Remove `cliff.toml`, `changelog-autoupdate.yml`, `update-unreleased.sh`, the sync-list
   entry, and the `Makefile` release target.
5. Rescope `release-tags-protect` (human step; see "Human prerequisites").

### Regenerating the changelog

Emit one section per release using release-please's own markup — `##
[X.Y.Z](compare/vA...vB) (YYYY-MM-DD)` with `...` (three dots, not cliff's `..`),
`### Features` / `### Bug Fixes` / `### ⚠ BREAKING CHANGES` headings, and `*` bullets of
the form `* subject ([#NN](issue-url)) ([sha](commit-url))`.

Section membership is `feat`, `fix`, `perf`, `revert`, plus anything marked breaking —
exactly what release-please treats as releasable, which is what makes the result
consistent going forward. Derived from history:

| release | releasable commits |
| --------------- | ------------------------------------------------ |
| `1.0.0` | 7 `feat` (3 of them `feat!` breaking) + 4 `fix` |
| `1.0.1` | 1 `feat(ci)` + 2 `fix` |
| `1.0.2` `1.0.3` | none — release-please would never have cut these |
| `1.0.4` | 1 `fix(sync)` (#120) |

Two deliberate differences from the current file:

- The three `feat!` commits in `1.0.0` move under a `### ⚠ BREAKING CHANGES` heading
  instead of cliff's inline `❗` prefix inside Features.
- Two `fix(ci)` commits (#92, #94) that the current `1.0.0` section omits are included.
  `fix(ci):` has type `fix`, so release-please surfaces it; cliff's `^ci` skip rule
  matched only the message prefix and never applied.

`1.0.2` and `1.0.3` remain absent, matching both cliff's current output and what
release-please would have produced — those ranges held no user-visible changes. The tags
and GitHub Releases for them are untouched.

Author attribution is dropped relative to cliff's `- ([sha](url)) - Michael I Chen`
format. Set `include-commit-authors: true` in `release-please-config.json` to keep it,
and apply the same choice to the regenerated historical sections so old and new match.

## Failure modes

| Failure | Behaviour | Mitigation |
| ---------------------------------------------- | -------------------------------------------------- | --------------------------------------------------------------------------------- |
| Release job re-run after a successful release | Tag exists → exit 0 | Manifest/tag idempotency check |
| Release PR merged but tag push fails | Manifest is ahead of tags; no release published | Re-run `workflow_dispatch`; idempotency check makes it safe |
| `v1` move fails after `v1.0.5` is created | New release exists, alias stale | Re-run; alias move is an unconditional force-update |
| Transient API error on the release-state check | Ambiguous: is it released or not? | Only a definitive not-found proceeds; any other error exits 1 rather than tagging |
| `workflow_dispatch` aimed at a feature branch | Would tag that branch and drag `vN` onto it | Job gated on `github.ref == 'refs/heads/main'` |
| Merged release PR keeps `autorelease: pending` | release-please stops opening release PRs, silently | release-please creates the Release itself, so it clears its own label |
| App token unavailable (`APP_ID` unset) | No PR, or PR with no CI | Guard the job on `vars.APP_ID != ''`, matching existing workflows |
| markdownlint regression on generated changelog | Release PR fails required checks | Directive fix above; caught on the first release PR |

## Testing

- `npx release-please release-pr --dry-run --repo-url=michen00/boilerplate-sync
--release-type=node` is the oracle. Read-only, needs no write access, and is the same
  command used to validate this design. Document it as the pre-merge check. Note the
  CLI's `--release-type` flag is unrelated to the action input of the same name — the
  CLI accepts it alongside a config file; the action does not.
- `actionlint` and `pre-commit` must pass on `release.yml`.
- Verify the tag job's idempotency check by dispatching it twice; the second run must
  exit 0 without touching anything.
- After release 1.0.5: confirm the tag is annotated, `v1` points at the same commit,
  `release-provenance.yml` ran, and `gh attestation verify` passes.

## Human prerequisites

Rescope `release-tags-protect` (ruleset id `17255321`). Nothing else — no new secrets;
`vars.APP_ID` (3959221) and `secrets.APP_PRIVATE_KEY` already exist.

`PUT` replaces a ruleset wholesale, so every field is restated:

```sh
gh api -X PUT repos/michen00/boilerplate-sync/rulesets/17255321 --input - <<'JSON'
{
  "name": "release-tags-protect",
  "target": "tag",
  "enforcement": "active",
  "conditions": { "ref_name": { "include": ["refs/tags/v*.*.*"], "exclude": [] } },
  "rules": [ { "type": "update" }, { "type": "deletion" } ],
  "bypass_actors": [
    { "actor_id": 5, "actor_type": "RepositoryRole", "bypass_mode": "always" }
  ]
}
JSON
```

Equivalent in the UI (**Settings → Rules → release-tags-protect**): set the target
pattern to `refs/tags/v*.*.*`, untick **Restrict creations** and **Require signed
commits**, leave **Restrict updates** and **Restrict deletions** ticked.

Note that dropping `creation` lets any write-access principal create a `v9.9.9` tag.
That is the repo owner and the App only, so it is not a practical exposure — but it is
the one protection genuinely given up here, as distinct from `required_signatures`,
which enforces nothing today.
